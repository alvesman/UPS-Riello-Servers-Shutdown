Authentication

This document describes the authentication mechanisms (or lack thereof) in the Riello UPS Servers Shutdown system.

Current Implementation

⚠️ Important: The system has no built-in authentication. It is designed for trusted local network environments.

Dashboard API

  • Authentication: None
  • Authorization: None
  • Access Control: Network-level only

All API endpoints are open and accessible to anyone who can reach the server on port 8080.

Server-Client Protocol

  • Authentication: None (hostname-based identification only)
  • Encryption: None (plain TCP)
  • Validation: Hostname accepted without verification
# Client identification - no authentication
message = {
    "type": "connect",
    "hostname": socket.gethostname()  # Trusted implicitly
}
self.socket.send(json.dumps(message).encode())

UPS API Connection

  • Protocol: HTTPS
  • Certificate Validation: Disabled (for self-signed certificates)
# SSL verification disabled
ctx = ssl.create_default_context()
ctx.check_hostname = False
ctx.verify_mode = ssl.CERT_NONE  # Accepts any certificate

Network-Level Security Recommendations

Since the application lacks built-in authentication, security must be implemented at the network level:

1. Firewall Configuration

# Allow only internal network access to dashboard
iptables -A INPUT -p tcp --dport 8080 -s 192.168.1.0/24 -j ACCEPT
iptables -A INPUT -p tcp --dport 8080 -j DROP

# Allow only internal network for server connections
iptables -A INPUT -p tcp --dport 5226 -s 192.168.1.0/24 -j ACCEPT
iptables -A INPUT -p tcp --dport 5226 -j DROP

# Allow UDP discovery only internally
iptables -A INPUT -p udp --dport 5225 -s 192.168.1.0/24 -j ACCEPT
iptables -A INPUT -p udp --dport 5225 -j DROP

2. Network Segmentation

  • Deploy server and clients on isolated management VLAN
  • Restrict dashboard access to administrator workstations only
  • Use network ACLs to limit client-server communication

3. Reverse Proxy (Optional)

Add authentication via reverse proxy for dashboard access:

# nginx configuration with basic auth
server {
    listen 443 ssl;
    server_name ups-dashboard.internal;
    
    ssl_certificate /etc/ssl/certs/ups.crt;
    ssl_certificate_key /etc/ssl/private/ups.key;
    
    auth_basic "UPS Dashboard";
    auth_basic_user_file /etc/nginx/.htpasswd;
    
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

Trust Assumptions

The system assumes:

  1. Network Trust: All devices on the network are authorized
  2. Hostname Trust: Clients accurately report their hostname
  3. UPS Trust: The UPS JSON API returns accurate data
  4. Physical Security: Server hardware is physically secure

Security Considerations

Potential Risks

RiskImpactMitigation
Unauthorized dashboard access Configuration changes, forced shutdown Firewall rules, reverse proxy auth
Rogue client connection False client in dashboard, resource consumption Network segmentation
Man-in-the-middle on client connection Unauthorized shutdown commands VPN or network isolation
UPS API spoofing False battery readings, unnecessary shutdown Network isolation, certificate pinning (not implemented)

Best Practices for Deployment

  1. Deploy on isolated management network
  2. Use firewall rules to restrict access
  3. Consider VPN for remote administration
  4. Monitor logs for unauthorized access attempts
  5. Regularly audit connected clients list
